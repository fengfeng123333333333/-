# S3 · 离线授权码（实施记录）

> 与计划 PPT 的 S3 完全不同：原计划是「在线三端点 + 6 小时心跳」，
> 本步按需求方 2026-11-12 的决定改为**离线授权码**，不部署服务器、不联网、不心跳。
> 改动理由与取舍见第一节，安全边界见第五节，发码操作见第九节。

---

## 一、与计划的差异

| | 原计划（在线租约） | 实际实现（离线授权码） |
| :-- | :-- | :-- |
| 依赖服务器 | 要，24 小时不能停 | **不要** |
| 客户端联网 | 要（每 6 小时心跳） | **不要** |
| 撤销某台设备 | 能，靠心跳生效 | 不能，只能等有效期到期 |
| 换机器 | 服务端重新绑定 | 重新输入同一张码即可 |
| 有效期 | 服务端给租约 | 本地记录首次激活时间 + 30 天 |
| 交付形态 | 一个 Web 服务 | 一个命令行签发工具 + 客户端内置公钥 |

决定由需求方拍板：**一码通用（码池）+ 30 天有效期**。
30 天恰好补上码池最大的短板——码即使流出去，最多也只能用满一个月。

## 二、技术选型：为什么没用 Ed25519

原方案写的是 Ed25519。开工第一件事做 API 探测，结果：

```
error CS0246: 未能找到类型或命名空间名"Ed25519"
```

反射 `System.Security.Cryptography 10.0.0.0` 确认：**.NET 10 的 BCL 里没有 Ed25519**（它不在 .NET 9/10 的公开 API 内），
只有 `ECDsa` 与 NIST 曲线。引第三方库（NSec）能拿到 Ed25519，但为这点收益增加一个供应链依赖不划算。

**改用 ECDsa P-256 + SHA-256 + IEEE P1363 定长签名**。实测结论：

| 验证项 | 结果 |
| :-- | :-- |
| P1363 签名长度（连续 3 次） | 稳定 64 字节 |
| 正常验签 | True |
| 改签名一位 / 改数据一位 | 均 False |
| 仅导入公钥能否验签 | 能 |
| **仅导入公钥尝试签名** | **抛 CryptographicException** |
| 另一把密钥签的码用本公钥验 | False |

最后一条是整套授权的根基：客户端只有公钥，反编译也造不出码。

一处坑：`SignData` 不显式指定格式时，在 Windows 上这次恰好也返回 64 字节，但那是平台相关行为
（Linux 上 OpenSSL 可能给 DER 变长）。代码里**显式传 `DSASignatureFormat.IeeeP1363FixedFieldConcatenation`**，
并有断言锁死「必须 64 字节」，底层换实现会立刻红。

## 三、授权码格式

Base32（Crockford）编码，总长 **120 字符**，可整段粘贴，粘贴时连字符、空格、大小写都会被忽略。

| 偏移 | 字节 | 字段 | 说明 |
| :-- | :-- | :-- | :-- |
| 0 | 1 | version | 格式版本，当前 1。不匹配直接拒绝，不会误解析成乱码 |
| 1 | 1 | keyId | 公钥编号，为将来换密钥留位 |
| 2..5 | 4 | serial | 随机序号，仅用于区分批次 |
| 6..7 | 2 | issuedDay | 签发日，自 2026-01-01 起的天数（可表示 179 年） |
| 8..9 | 2 | validDays | 激活后的有效天数 |
| 10 | 1 | flags | 预留功能位 |
| 11..74 | 64 | signature | ECDSA P-256 / SHA-256 / P1363 定长签名 |

选 Crockford Base32 而不是 Base64：字母表去掉 I、L、O、U，用户抄错也认得出来；
解码时仍把 I/L 当 1、O 当 0 容错。代价是比 Base64 长约 13%（106 → 120 字符），
但码是复制粘贴的，不是手打的，长度不敏感。

## 四、有效期怎么算

**从首次激活起算 30 天，不是从签发日算。** 两个原因：
一是码池要能囤，从签发日算意味着没用完的码会自然作废；
二是需求方按月收，从激活日算才对应得上。

四条规则互相咬合：

1. **同一张码重复激活不重置首次激活时间**。否则用户重装一次就白续一个月。
2. **换一张新码则重新计时**。买了新的就该从今天开始算。
3. **时间回拨无效**。每次启动取 `max(当前时间, 历史上记录的最晚时间)` 作为计算基准。
   用户把系统时间调回上月，剩余天数仍是真实值，而且不会误伤——程序不报错，只是不给他便利。
4. **凭证加密落盘**。AES-GCM，密钥由机器码派生。文件被拷到别的机器上解不开，
   顺手也挡住了「拷一份给朋友」。

## 五、安全边界（能防什么、防不住什么）

**防住了：**

- **伪造授权码** —— 没有私钥签不出。客户端只有公钥。
- **篡改授权码** —— 改任何一位，验签失败（测试逐字节验证过）。
- **手改到期时间** —— 凭证是密文，改了就解不开。
- **回拨系统时间** —— 见第四节第 3 条。
- **复制凭证文件到别的机器** —— 密钥绑机器码，解不开。

**防不住（离线授权的物理上限，写代码解决不了）：**

- **删掉凭证文件重新激活** —— 等于续命一个周期。这是纯离线的固有限制。
- **码在有效期内被多人使用** —— 码池模式本身就不绑机器，需求方已接受。
- **逆向内存拿到密钥** —— 任何本机加密手段都挡不住有决心的人。
- **远程吊销** —— 没有服务器，发出去的码收不回来，只能等它过期。

要突破这些限制只有一条路：重新引入服务端。当前选择是「用可控的扩散风险换零运维成本」。

## 八、过程中发现并修掉的缺陷

1. **授权码长度检查顺序错了**。原实现先解码再判长度，少复制一个字符时尾部补齐位非零，
   用户收到的是「校验位异常」——完全不知道该怎么办。改为先数字符（忽略分隔符）再解码，
   现在提示「应为 120 个字符，实际 119 个，通常是复制时少了一段」。
2. **激活成功后程序直接消失**。`ShutdownMode` 默认 `OnLastWindowClose`，
   原来先 `login.Close()` 再开主窗口，关窗瞬间没有任何窗口，进程直接退出。
   改为先开主窗口再关激活窗。这个坑 S1 就埋下了，因为开发模式直接进主界面所以一直没暴露。
3. **测试脚本写入被输入法污染**（工具问题，非产品缺陷）。`set_text` / ValuePattern 在中文输入法下
   会写出 `zhen040MVG…`、`2040MVG…` 这种多前缀的值。改用剪贴板 + Ctrl+V，与真人操作一致。

## 九、怎么发码（操作手册）

```bat
REM 1. 生成密钥对（只做一次）。口令至少 8 位，从环境变量读，避免进命令行历史
set FBAUTO_KEY_PASS=你的口令
fbauto-keygen initkey

REM 2. 批量签 50 张，激活后 30 天有效
fbauto-keygen gen --count 50 --days 30

REM 3. 验一张码（顺带演示改一位必须失败）
fbauto-keygen verify "040MVG2J..."
```

产物位置：

- 私钥：`C:\Users\DZH\FbAutoSecrets\license_private.key`（口令加密，**必须备份**）
- 公钥：`C:\Users\DZH\FbAutoSecrets\license_pubkey.b64`（可公开）
- 码批次：`C:\Users\DZH\FbAutoSecrets\codes_<时间戳>.txt`

**私钥丢了会怎样**：已发出的码无法续期，也无法再签新码，只能换密钥重发所有码。
**换密钥会怎样**：所有旧码立即失效，客户端也要换公钥重新发布。所以密钥对要长期保管。
