## 一、为什么先做这一步

`facebook.com:443` 在本机直连超时（DNS 正常，缺境外出口）。页面动作没条件验收，
硬做只能靠「代码看起来对」——这正是项目一直避免的做法。

但这四件事里真正容易出错的部分**与页面无关**：

- 尺寸够不够、比例偏不偏
- 账号和图片怎么对应
- 有弹窗先关哪个、没弹窗该不该动
- 删除顺序会不会错位

这些全是纯判断。判断写错，页面通了以后照样错，而且错得隐蔽（删错视频、同账号头像背景不一致）。
所以先把判断做成可单测的纯逻辑，页面层只留一层薄壳。

一个附带发现：原版「继续」按钮的选择器是
`div[aria-label='[object Object]'] span:has-text('继续')` ——

## 三、四件套各自定成了什么样

### 3.1 封面尺寸：两层判断

原版只有「上传后看页面反应」这一层。这里加了一层本地的：

| 层 | 时机 | 作用 | 是否原版行为 |
| :-- | :-- | :-- | :-- |
| 本地预校验 | 上传**前** | 挡掉注定失败的图，省一次往返 | 否，本步增强 |
| 页面提示判定 | 上传**后** | 等 `请选择其他封面照片` 出现，弹了就换图 | 是 |

本地判定分三档而不是二元，因为「小到被拒」和「小但会被拉伸接受」处理方式完全不同：

- `Rejected`：读不出、格式不支持、超 15MB、小于 400×150
- `AcceptedWithWarning`：低于推荐 820×312、超 100KB、比例偏离（会被裁切但能传）
- `Accepted`：都对

阈值来自平台规定，**做成数据不做成硬编码**（`CoverSizeRule`），平台改了只改默认值。
查证于 2026-11-12，多个独立来源一致：桌面显示 820×312、移动端 640×360、
最小上传 400×150、官方建议 ≤100KB、格式 JPG/PNG。
比例区间取 `[2.2, 3.0]`，覆盖 820×312(2.63) 与设计画布 820×360(2.28)。

### 3.2 随机取图：账号级确定性分配

一句话需求里藏着一个坑：「同一账号同一张」+「不同账号不同」。

- 每次调用随机 → 同账号头像和背景图不一样，违反前半句
- 每次按账号哈希取模 → 同账号稳定，但 2 张图 3 个账号必撞，违反后半句

做法：按 seed 对图片**确定性洗牌**，再按账号顺序依次取用。
前 `min(账号数, 图片数)` 个账号保证互不相同；账号比图多时给出警告而不是假装没事。
同一 seed 同一套分配，可复现、可续跑。

目录侧：白名单 `.webp/.jpg/.jpeg/.png`（来自原版串），大小写不敏感，0 字节文件跳过并记账，
非图片文件静默忽略（目录里放个 readme.txt 不该刷警告），结果按文件名排序保证多次扫描顺序一致。

### 3.3 通知弹窗：规则表 + 兜底

规则表按优先级排（`发生了什么` 是异常对话框，必须先关），决策器一次只决定**一步**：

| 观测到的情况 | 动作 |
| :-- | :-- |
| 没有可见弹窗 | **什么都不做** |
| 某条规则可见且可用 | 点它 |
| 可见但按钮禁用 | 按 Escape，理由写明是哪条不可用 |
| 可见但不在规则表里 | 按 Escape 兜底 |

「没有弹窗时什么都不能做」单独列一条，是因为按一下 Escape 可能关掉正在编辑的资料弹窗，
前面填的东西全丢。这是整个弹窗逻辑里唯一会造成数据丢失的分支。

单轮上限 3 次（原版同类轮询用的是 3 次），防「关掉一个又冒一个」的空转。

`[object Object]` 那条缺陷没有复刻：给了可用的选择器，但默认不启用（`OptIn`）。
文案匹配 `has-text('继续')` 误伤面大，点错「继续」可能跳过本该填的内容。

### 3.4 失败草稿：倒序移除

原版按位置从小到大点。**这里改成倒序，是有意修正**：

> 删掉第 1 条后，第 2 条会前移成第 1 条；这时再去点「第 2 个移除按钮」，点到的是原本的第 3 条。

失败视频 ≥3 条时几乎必然删错。倒序从最大的位置往前删，前移只影响已经处理过的位置。

其余照抄原版行为：位置不存在 → 跳过并说明；按钮不可用 → 跳过并说明；日志文案一字不改，
真机对比时能逐行对上。

### 6.3 过程中发现并修掉的缺陷

1. **`SkipLocally` 只记日志、不把图从候选里移除**。表现是：本地预校验已判定某张图不合格，
   下一次 `TakeNext()` 还是把它取出来上传一遍。白跑一趟，还会把失败次数记在页面上。
   由 `本地跳过不占上传次数` 这条用例抓出来（第一次跑就红了），修法是在 `SkipLocally` 里移除候选，
   并处理「先取出再本地校验」的流程（把已计的上传次数退回去）。
2. **`build/*.cmd` 五个脚本全是 UTF-8 存中文注释，在中文 Windows 下是坏的**。
   cmd.exe 按系统 ANSI 码页（936）解析 `.cmd`，UTF-8 中文被解成乱码后把行切断，
   表现为「`build\test.cmd` 报一堆 `'笉渚濊禆绯荤粺' 不是内部或外部命令`」。
   这是历史遗留（前面几步都是用 dotnet.exe 直接跑的，没从这里走）。
   已把 5 个脚本全部改为纯 ASCII（注释与提示改英文，逻辑一字不改），
   并把 `new-profile.cmd` 生成的中文启动器名改成 `start-<别名>.cmd` —— 生成的文件名同样会被码页弄乱。
   修完用 `build\test.cmd` 跑通 357 条。
3. **JPEG「没有 SOF 段」的测试样本只有 10 字节**，被「文件头不足 12 字节」提前拦下，
   测的根本不是 SOF 分支。改成 12 字节的正常长度样本。这是测试自身的缺陷，不是产品的。

### 6.4 踩的坑

1. **提取串要先修编码再看**。`docs/evidence/extracted/*.cn.txt` 里中文与选择器大量呈现为
   `慦嬀栀爀攀昀⨀...` 这种形态 —— 那是 UTF-16LE 字节被按单字节解出来的结果。
   直接在脏文件里 grep 关键词几乎什么都找不到，必须回到原始 DLL 按 UTF-16LE 重新扫描。
   重扫后四个方法的串一次性全出来了。
2. **方法名归属要看类名前缀，别按名字猜**。`CheckCoverSizeErrorAsync` 名字像视频上传，
   实际属于 `ProfileEditService`（资料修改的封面/背景图）。按名字猜会把它挂到错的流程上。
3. **阈值必须查证，不能凭印象写**。视频封面常见的 1280×720 是错的场景 ——
   这里要的是主页封面 820×312、最小 400×150。阈值一旦写进代码就会被当成事实，
   所以先查多个独立来源、确认一致再落成常量，并把来源与查证日期写进注释。

### 6.6 与计划口径的差异

计划 P08 的验收是「10 条视频成功率 ≥8」。本步交付的是它的通用件，不是它本身。

差异不在标准，在顺序：先把不依赖外网、且被三条主线复用的判断逻辑做完并测牢，
出口通了以后页面层才有东西可挂。若把顺序倒过来，页面动作会和这些判断纠缠在一起，
到时候一处尺寸判断出错，要连带怀疑是页面没加载、还是选择器变了、还是逻辑写错了。
